1"""SQLModel table definitions. 

2 

3Table classes here are plain SQLAlchemy models underneath (SQLModel is a thin 

4Pydantic layer on top) - all async DB access goes through SQLAlchemy's own 

5AsyncEngine/AsyncSession (see engine.py), never SQLModel's sync-oriented 

6`Session`/`create_engine` helpers. Columns SQLModel's type system doesn't 

7know natively (`TSVECTOR`, `pgvector.Vector`) use the `sa_column=` escape 

8hatch, same as plain SQLAlchemy would need. 

9 

10Note on `search_vector`: this is a plain, app-maintained TSVECTOR column, 

11NOT a Postgres `GENERATED ALWAYS AS (...) STORED` column - a generated 

12column's expression can only reference columns in its own table, but the 

13document body lives in `Content.doc` (joined via `hash`), not in 

14`Document` itself. It's kept in sync by `update_document_search_vector()` 

15in the search module (ported from the TS `updateDocumentSearchVector`), 

16called wherever a document's title/path/body changes - the same discipline 

17the working TS/Postgres implementation already uses successfully. 

18 

19Per-model embedding tables (`embeddings_<slug>`) are NOT defined here - 

20they're created dynamically at runtime once a model's dimension is known 

21(see search/vector.py, Phase 5), mirroring the TS version's lazy vector 

22column creation but non-destructively (one table per model, never dropped 

23on a model switch). 

24"""

45# No explicit `schema=` anywhere below, deliberately: qmd-py's isolation 

46# from the TS/Postgres reference implementation's tables (which live in 

47# `public` on the same `qmd` database - see the plan's "Single Postgres, 

48# forever" decision) comes entirely from the connection's `search_path` 

49# (set to just `qmd_py` in config.py), the same way the TS implementation 

50# itself creates unqualified tables that land whichever schema its own 

51# connection defaults to. 

52# 

53# An earlier version of this file set `SQLModel.metadata.schema = "qmd_py"` 

54# explicitly and schema-qualified every FK target string. That produced a 

55# permanent, recurring false-positive `alembic check`/autogenerate diff: 

56# Alembic's reflection of the connection's *default* schema normalizes 

57# table/FK objects to `schema=None` (since from the connection's point of 

58# view, unqualified access already means "the current schema"), while an 

59# explicit `schema="qmd_py"` on the metadata side is a *different* Python 

60# representation of the exact same schema - and Alembic's constraint 

61# comparator does a structural comparison that doesn't collapse the two, 

62# so it proposed dropping and recreating the same FKs forever. Leaving 

63# schema unset here makes both sides agree (`schema=None` on both), which 

64# is also simply less code.

85class Collection(SQLModel, table=True): 

86 """Replaces the TS version's bare `documents.collection` TEXT tag with a 

87 real, owned entity - the prerequisite for per-collection ACL. `name` is 

88 scoped per-owner (UNIQUE(owner_user_id, name)), not globally unique like 

89 the TS version's `store_collections.name` primary key.

91 Per-path context text (the TS version's `context add <path> "text"`,

94 supports many contexts per collection, keyed by path prefix."""
